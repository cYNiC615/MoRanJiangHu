# Homebrew AI Native 现状与精简边界

> 日期：2026-06-15
>
> 目的：整理当前仓库的实际架构状态、已确认的 homebrew 项目锚点，以及后续精简边界。本文不是新的执行计划，只作为后续制定个人 homebrew 定制路线前的事实底稿。

## Homebrew 项目锚点（已确认）

这些是当前 homebrew 方向的硬边界，后续计划、删减和重构优先按这里判断。

- 默认体验改为现代都市，不做武侠/修仙默认背景。未来可以扩展近未来科幻，但主体验不再围绕江湖、宗门、修仙成长线展开。
- 现有“创意工坊”本质上包含模式包、世界书注入、本地导入、云端投稿和下载接口。后续只把“本地模式包/世界书注入”视作可保留的内容风味切换能力，用它服务现代都市默认化；云端社区投稿、同人模式包分享不作为目标。
- 不做任何“同人”“小说分解”“小说拆解后改编”相关功能。相关工作台、提示词、模型字段、创意工坊桥接、章节滑窗和分歧线能力都可以进入移除清单。
- 不做移动端，不做 APK。移动端 UI、Capacitor、APK 构建、APK 更新、移动端 OAuth/下载校验等都可以进入移除清单。
- 不做云端发布和社区 UGC。Cloudflare 部署暂时保留为待定项，先不马上删除，后续单独判断它是否只承担网站托管/API 代理价值。
- GitHub 云同步、多设备同步、在线更新能力可以去掉。必须完整保留的是本地设置、API 配置、本地游戏存档、存读档和必要的导入导出能力。
- 核心玩法仍按 AI native RPG harness 理解：AI 负责生成/扮演/规划，本地代码负责上下文、状态、协议解析、存档和 UI。

## 0. 基本判断

这个项目应按“重 AI native harness”理解，而不是按传统确定性 RPG 引擎理解。

当前核心不是“用代码完全模拟世界”，而是：

- 前端维护一组较大的 RPG 状态树。
- 主剧情模型输出正文、短期记忆、变量规划和剧情规划。
- 独立 AI 链路继续处理变量生成、规划分析、世界演变、地图更新、正文润色、记忆召回等任务。
- 本地代码负责拼装上下文、解析协议、应用命令、规范化状态和提供 UI。

如果后续能把某些高风险逻辑改成本地状态机，稳定性会更好；但如果工程复杂度过高，保留 AI harness 方案本身也是合理路线。这个项目和 Memento 项目没有直接关系，除非后续发现某些通用工程方法值得借鉴，否则不应混用两边的产品目标。

## 1. 当前事实总览

- AI 服务拆分、`useGame` 主流程拆分、提示词运行时收口已经基本成为现状。
- 主剧情输出协议已经从“主剧情直接写命令”转为“主剧情写 `<变量规划>` / `<剧情规划>`，独立链路再生成结构化命令”。
- 小说分解、同人规划、章节滑窗和分歧线不是纸面功能，已经有 UI、模型、提示词和运行时注入；但它们不符合当前 homebrew 方向，可以进入移除清单。
- 剧情、女主规划、世界模型已有较完整的新结构，但章节切换、世界事件推进仍主要靠 AI 提示词和命令写回，不是本地确定性状态机。
- COT / 输出格式里的若干历史冲突已经在当前协议中修正，例如 `<judge>` 只嵌入正文、行动选项可独立输出、主剧情转向规划草稿。
- 项目工程已经分层，但 `App.tsx`、主回合工作流、状态转换、命令处理和大量外围功能仍然偏重。

## 2. 已完成或已成为现状的内容

### 2.1 基础工程拆分

已经完成的现状：

- `services/aiService.ts` 已收口为导出层。
- 文本 AI 业务主要在 `services/ai/storyTasks.ts`。
- 文本请求统一经由 `services/ai/chatCompletionClient.ts` 的 `请求模型文本`。
- `hooks/useGame.ts` 不再独自承担全部流程，主流程已拆到多个 `hooks/useGame/*Workflow.ts` 文件。
- `hooks/useGame/sendWorkflow.ts`、`openingStoryWorkflow.ts`、`worldEvolutionWorkflow.ts`、`planningUpdateWorkflow.ts`、`variableModelWorkflow.ts` 等已经成为核心工作流。

判断：这一部分可以视为已完成，不需要再作为后续重构重点。

### 2.2 主剧情输出协议已从“直接命令”转向“规划草稿”

当前协议已经明确：

- 主剧情负责输出 `<正文>`、`<短期记忆>`。
- 本回合已发生、需要落变量的内容写入 `<变量规划>`。
- 后续承接、章节余波、强制触发、镜头余波写入 `<剧情规划>`。
- 最终结构化命令由独立变量生成链路处理。

相关落点：

- `prompts/core/format.ts`
- `prompts/core/cot.ts`
- `prompts/core/cotHeroine.ts`
- `prompts/runtime/variableGeneration.ts`
- `prompts/runtime/variableModel.ts`
- `hooks/useGame/variableModelWorkflow.ts`

判断：这是当前架构的真实现状，应作为后续 homebrew 计划的基础，而不是回到旧 `<命令>` 主剧情方案。

### 2.3 小说分解滑窗注入已经接线

当前已经实现：

- `services/novelDecompositionInjection.ts` 构建实时章节滑窗。
- 主剧情链路读取 `main_story` 注入。
- 规划分析链路读取 `planning` 注入。
- 世界演变链路读取 `world_evolution` 注入。
- 注入标签包括 `【前一章节内容】`、`【当前章节内容】`、`【下一章节内容】`，其中不同链路保留的信息量不同。

相关落点：

- `services/novelDecompositionInjection.ts`
- `hooks/useGame/sendWorkflow.ts`
- `hooks/useGame/planningUpdateWorkflow.ts`
- `hooks/useGame/worldEvolutionWorkflow.ts`
- `components/features/Settings/NovelDecompositionSettings.tsx`

判断：小说分解滑窗不是纯计划，已经是现状。

### 2.4 剧情、规划、世界模型大多已改成新结构

已经看到实际模型：

- `models/story.ts`：`当前章节`、`下一章预告`、`历史卷宗`、`章节时间校准`。
- `models/storyPlan.ts`：当前章任务、跨章延续、待触发事件、镜头规划、换章规则。
- `models/heroinePlan.ts`：阶段推进、女主条目、互动事件、镜头规划。
- `models/fandomPlanning/story.ts`：当前对齐信息、同人任务、分歧线、待触发事件、换组规则。
- `models/fandomPlanning/heroinePlan.ts`：同人女主阶段、原著关系线、分歧线关联。
- `models/world.ts`：待执行事件、进行中事件、已结算事件、世界镜头规划、江湖史册。

相关支持也已存在：

- `hooks/useGame/storyState.ts` 中有规范化逻辑。
- `utils/stateHelpers.ts` 支持这些根路径命令。
- `hooks/useGame/responseCommandProcessor.ts` 会规范化并写回这些状态。

判断：模型重构已明显落地，不是纸面计划。

### 2.5 部分 COT 冲突已修正

已修正或基本修正的点：

- `<judge>` 已明确不是顶层标签，只能嵌入 `<正文>`。
- 判定行结果字段已明确后置为 `｜结果=...`。
- `noControl.ts` 已允许在正文之外输出独立 `<行动选项>`。
- 主剧情 COT 和女主 COT 均已使用 `Step0~Step14`。
- 女主 COT 变体在 `systemPromptBuilder.ts` 有槽位映射。

判断：很多历史输出协议冲突已不再是当前问题。

## 3. 部分完成但仍需确认的内容

### 3.1 切章/换组仍主要靠 AI 执行

理想的稳定切章流程应包括：

1. 归档旧章到 `剧情.历史卷宗`
2. 迁移跨章延续事项
3. 清空旧章专属规划
4. 切换当前分解组
5. 初始化新章任务、事件、镜头

当前代码层面已有字段、提示词和命令落地能力，但核心决策和执行顺序主要由规划分析 AI 输出命令完成。

换句话说：

- 状态树支持切章。
- 提示词强约束切章门禁。
- 命令系统可以写入结果。
- 但本地代码没有一个明确的确定性 `chapterTransitionEngine` 来保证流程总是按门禁执行。

判断：部分完成。后续如果要大精简，需要决定是否保留 AI 切章，还是把切章改成本地状态机。

### 3.2 小说分解系统实现较多，但复杂度很高

小说分解相关能力已经存在，包括：

- 数据集、章节、分段、时间线事件、关键事件、角色推进、可见性边界。
- 小说分解工作台 UI。
- 注入快照与实时滑窗。
- 同人模式下的原著锚点、抢跑约束、分歧线提示词。

但它同时带来很大复杂度：

- 对原创 homebrew 不一定必要。
- 对非同人玩法可能过重。
- 如果不做“原著章节对齐”类玩法，这部分可能成为维护负担。

判断：能力已实现，但是否保留要看 homebrew 方向。

### 3.3 `App.tsx` 和部分工作流仍然过重

虽然已经拆分，但仍可观察到：

- `App.tsx` 仍负责大量横切逻辑，如更新、心跳、图片迁移、拍卖行、诊断、云同步等。
- `hooks/useGame/sendWorkflow.ts`、`storyState.ts`、`stateTransforms.ts`、`responseCommandProcessor.ts` 仍非常大。
- 很多功能并非核心聊天 RPG 必需，却已经深度接入。

判断：工程层只是“从极重变成分层较重”，还没有达到适合个人 homebrew 的轻量状态。

### 3.4 部分历史 COT 口径已经不完全同步当前协议

当前协议已经改变了早期 COT 设计中的一些前提，例如：

- 关注 `<命令>` 与主剧情直接命令边界。
- 部分 Step 数描述与当前开局 COT 现状不一致。
- `<动态世界>` 顺序问题已被当前 `<变量规划>` / `<剧情规划>` 方案改变上下文。

判断：这类历史问题只保留为事实结论，不再作为后续执行计划。

## 4. 仅计划或未形成强代码保障的部分

### 4.1 确定性章节状态机

没有看到一个本地确定性状态机统一负责：

- 读取当前章门禁。
- 判断是否切章。
- 自动归档历史卷宗。
- 清理旧章规划池。
- 初始化新章规划池。

现状更像“提示词驱动的 AI 规划分析 + 命令写回”。

判断：如果我们后续想降低 AI 不稳定性，这是候选重构点；如果要精简工程，则可以继续保留 AI harness，不急着改成状态机。

### 4.2 完整的本地剧情/世界事件执行器

世界结构已经有待执行、进行中、已结算事件，但是否启动、推进、结算仍主要由世界演变 AI 判断。

没有看到传统游戏意义上的：

- 事件调度器
- 条件表达式解析器
- 本地事件触发器
- 可测试的事件状态迁移表

判断：当前是 AI 事件维护池，不是确定性事件引擎。

### 4.3 部分功能的实际目录形态仍然分散

例如同人相关能力当前更像是：

- `models/fandomPlanning/` 已存在。
- `prompts/runtime/fandomPlanningAnalysis.ts` 存在。
- 但没有形成更细的独立提示词目录树。

判断：后续不应继续为了补齐目录而补齐目录，而应按 homebrew 精简方向直接判断保留或移除。

## 5. 已确认废弃、暂缓与保留边界

这一节按当前已确认锚点更新，不再把所有内容都写成“候选”。

### 5.1 已确认进入移除清单

这些方向已经不属于 homebrew 目标，可以后续分阶段删 UI、删服务、删模型字段、删提示词和删测试：

- 武侠/修仙作为默认体验的开局、文案、主题和世界观默认值。
- 同人功能、小说分解工作台、小说分解运行时注入、小说分解创意工坊分享、同人剧情规划、同人女主规划、原著章节滑窗和分歧线系统。
- 移动端专用 UI、移动端快捷菜单、Capacitor 原生壳、APK 构建、APK 更新、Android OAuth deep link 和 APK 发布校验。
- GitHub 云同步、多设备同步、在线更新、WebDAV/对象存储同步中专门服务跨设备的产品入口。
- 社区 UGC、创意工坊云端投稿、云端下载、投稿账号绑定、社区预设自动提交 PR。

### 5.2 暂缓决定

这些不先删，等第一轮精简后再判断：

- Cloudflare Worker / Pages Functions：如果只承担网站托管、API 代理或未来轻量发布，可能暂留；如果主要服务社区、同步、APK、UGC，则可继续缩减。
- 图片生成与图床链路：用户尚未明确废弃视觉资产。如果定制版仍要图像表现，可以保留核心生图；如果目标变成纯文字 RPG，再整体冻结。
- 管理后台、在线统计、联机状态：如果只服务公共运营，倾向移除；如果有本地诊断价值，可以拆出极小诊断页。

### 5.3 必须完整保留

这些是当前明确要保留的能力：

- 本地设置与 API 配置。
- 本地游戏存档、读档、导入、导出和 IndexedDB 基础能力。
- AI 主回合链路、提示词协议、变量生成、剧情规划、世界演变和命令落地。
- 现代都市默认题材所需的开局配置、世界书、状态树和 UI。
- 本地模式包/世界书注入能力，前提是它服务个人定制，不依赖社区投稿。

### 5.4 创意工坊的重新定位

当前“创意工坊”相关实现大致分成两层：

- 可保留层：`utils/workshopEngine.ts`、`data/creativeWorkshopModules.ts`、`data/workshopThemes/defaultWorkshopTheme.ts` 中的模式包、默认主题、题材配置、世界书注入、本地模块导入。
- 可移除层：`services/creativeWorkshop.ts` 中的云端投稿/下载 API、账号绑定，`services/workshopNovelDecomposition.ts` 和 `services/novelDecompositionWorkshopBridge.ts` 中的小说分解分享与同人模式包桥接。

默认主题当前仍是 `武侠`，这和 homebrew 锚点冲突。后续第一轮功能精简时，应把默认主题、默认开局、README 产品定位和题材配置一起改到现代都市口径。

## 6. 当前最值得保留的核心

无论后续怎么精简，以下部分建议暂时保留：

- `prompts/core/format.ts` 的标签协议。
- 主剧情 `<变量规划>` / `<剧情规划>` 分工。
- 独立变量生成链路。
- `models/character.ts`、`models/environment.ts`、`models/world.ts`、`models/story.ts` 的基础状态树。
- `hooks/useGame/sendWorkflow.ts` 的主回合链路。
- `hooks/useGame/responseCommandProcessor.ts` 的命令应用与状态规范化。
- 存档与 IndexedDB 基础能力。
- 设置页中的 API 配置能力。
- 现代都市默认化所需的本地模式包/世界书注入能力。

这些是 AI native RPG harness 的骨架。

## 7. 下一步建议

下一步不建议直接开始删代码。

建议先产出一张精简决策表，把模块分成四类：

- 核心保留：必须支撑 homebrew 主体验。
- 可配置隐藏：暂时不删，但 UI 不主动暴露。
- 冻结维护：保留代码，不继续加功能。
- 准备废弃：确认无用后分阶段删除。

然后再按模块逐个处理，避免继续为不属于 homebrew 方向的能力补字段、补提示词、补链路。
